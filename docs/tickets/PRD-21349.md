## Product design

### Goals / Non-goals

**Goals** (v1, user-visible capability — what an agent connected to Calendly can do on the requester's behalf):
- Discover the user's Calendly meeting types (event types) and their scheduling links.
- Check open availability for a given event type, and the user's busy blocks, so an agent can suggest or avoid times.
- List, inspect, and cancel the user's scheduled meetings (events).
- Inspect who is invited to a given meeting and whether they accepted/canceled.
- Generate a single-use scheduling link an agent can hand to someone else to pick a time themselves (the normal way a human shares a Calendly link).
- Identify which Calendly account is connected (name/email/scheduling URL), since several tools need the account's own user/organization URI as an input.

**Non-goals** (v1):
- Creating/editing event types, managing availability schedules, or changing team/organization membership — these are account-configuration actions a human does inside Calendly itself, not something the ticket or the conduit.wyre.ai reference asks an agent to automate.
- Contacts (Calendly's CRM-style contact list), routing forms, webhooks, meeting recaps/notetaker transcripts, and the activity log — all admin/Enterprise-tier surfaces not implied by "connect Calendly for scheduling", and the activity log and meeting-recap transcript endpoints require an Enterprise subscription we have no evidence this account holds.
- OAuth app flow — the prior run already fixed this as a Personal Access Token integration (see Open Questions, assumption carried forward).
- GDPR-style data-deletion endpoints (`/data_compliance/deletion/*`) — destructive, compliance-specific, out of scope for a scheduling assistant.
- Creating an invitee directly via the Scheduling API (`POST /invitees`) — that endpoint is for Calendly's own embedded booking widget completing a booking a human just made on a Calendly page; it is not "an agent books a meeting for someone", and Calendly does not expose a generic "book this slot for this invitee" server-side action outside that embed flow.

### Acceptance criteria

- **AC1**: Given a valid Calendly Personal Access Token in the configured request header, When the agent calls the "list event types" tool, Then it returns the user's event types (name, duration, scheduling URL, active/kind) and can be filtered to active-only.
- **AC2**: Given an event type and a date window of 31 days or less, When the agent calls the "get available times" tool, Then it returns the open booking slots for that window; given a window longer than 31 days, Then the tool rejects the call with an `invalid_argument` error before calling Calendly (Calendly's own documented limit for this endpoint).
- **AC3**: Given valid credentials, When the agent calls the "who am I" tool, Then it returns the connected account's name, email, scheduling URL, and the user/organization URIs other tools need as input.
- **AC4**: Given valid credentials and optional filters (status, time window, invitee email), When the agent calls "list scheduled events", Then it returns the user's meetings within that scope, newest first by default.
- **AC5**: Given the UUID of one of the account's own scheduled events, When the agent calls "get scheduled event", Then it returns that event's full detail (start/end time, location, status, event type, invitee count). Given a UUID that does not belong to the authenticated account, Then the tool returns whatever not-found/forbidden result Calendly's own API returns for that token — access scoping is enforced by Calendly against the bearer token, this service does not do its own cross-tenant mixing (see §3 Non-functional).
- **AC6**: Given an event UUID, When the agent calls "list event invitees", Then it returns each invitee's name, email, status (active/canceled), and cancellation reason if canceled.
- **AC7**: Given an event UUID and an optional reason, When the agent calls "cancel scheduled event", Then the event is canceled in Calendly, and a subsequent "get scheduled event" call shows `status: canceled`. This tool is destructive (`destructiveHint: true`) and only accepts an explicit event UUID — no bulk/pattern-based cancellation.
- **AC8**: Given a user URI and a time window of 7 days or less, When the agent calls "list busy times", Then it returns the user's busy blocks (internal Calendly events plus external calendar conflicts where the user has "check for conflicts" enabled); given a window longer than 7 days, Then the tool rejects the call with `invalid_argument` before calling Calendly (Calendly's documented limit).
- **AC9**: Given an event type URI, When the agent calls "create scheduling link", Then it returns a single-use booking URL that can be shared with someone else to pick their own time; the agent itself is never shown as picking a slot on the invitee's behalf.
- **AC10** (cross-cutting, applies to every tool): Given the request is missing the required credential header, When any tool is called, Then the service returns an `unauthorized` structured error naming the missing header, without calling the Calendly API.
- **AC11** (cross-cutting): Given Calendly's API returns 429 or a 5xx, When a tool is called, Then the service maps it to a structured error (`rate_limited` / `upstream_error`, `retryable: true`) instead of crashing or returning a raw 500.
- **AC12** (cross-cutting, multi-tenant isolation): Given two concurrent requests carry two different tenants' Personal Access Tokens, When both call the same tool at the same time, Then each response reflects only its own token's data — no credential or response data crosses between the two requests (request-scoped context, no shared/global client cache).
- **AC13** (cross-cutting): Given the service is deployed, When `GET /health` is called with no credentials, Then it returns `200 {"status":"ok"}` regardless of Calendly API reachability.

## Tech design

### Conclusion

Build `MSPbotsAIFramework/calendly-mcp` as a new Python 3.12 + `uv` + FastMCP Streamable HTTP service (SOP main line A), following the same shape as other MSPbotsAIFramework vendor connectors: one stateless `/mcp` endpoint, credentials read per-request from an `Authorization`-style header, 9 tools (§3.4) that each wrap one Calendly REST endpoint 1:1 with no new business logic beyond the SOP's required input validation, pagination defaults, and error-envelope mapping. The core mechanism — read bearer token from header, call `https://api.calendly.com`, map `{title, message, details[]}` errors to the SOP envelope — is the same pattern every other vendor-mcp repo already uses; there is no architectural choice to make here beyond which 9 of Calendly's ~35 documented endpoints make the v1 cut (§"Decisions made by DEV01").

### Data & API contract

Base URL: `https://api.calendly.com`. All 9 tools are thin 1:1 wrappers; `{...}` below is the Calendly response shape, trimmed to the fields the tool returns (full passthrough minus internal/pagination noise the agent doesn't need).

| Tool | Calendly endpoint | Required params | Optional params | Notes |
|---|---|---|---|---|
| `calendly_get_current_user` | `GET /users/me` | — | — | Returns `{uri, name, email, scheduling_url, current_organization}`; callers use `uri`/`current_organization` as inputs to other tools |
| `calendly_list_event_types` | `GET /event_types` | — | `active`, `organization`, `user`, `count` (default 20, max 100), `page_token` | Returns `{collection:[{uri,name,duration,scheduling_url,kind,active}], has_more}` |
| `calendly_get_event_type_available_times` | `GET /event_type_available_times` | `event_type` (uri), `start_time`, `end_time` | — | **Window ≤ 31 days** (Calendly's documented limit) — validated client-side before the call, `invalid_argument` otherwise |
| `calendly_list_scheduled_events` | `GET /scheduled_events` | — | `user`, `organization`, `invitee_email`, `status`, `min_start_time`, `max_start_time`, `count`, `page_token` | Returns `{collection:[{uri,name,start_time,end_time,status,event_type,location}], has_more}` |
| `calendly_get_scheduled_event` | `GET /scheduled_events/{uuid}` | `uuid` | — | 404 from Calendly passes through as `not_found` |
| `calendly_list_event_invitees` | `GET /scheduled_events/{uuid}/invitees` | `uuid` | `status`, `email`, `count`, `page_token` | Returns `{collection:[{name,email,status,cancellation:{reason}}]}` |
| `calendly_cancel_scheduled_event` | `POST /scheduled_events/{uuid}/cancellation` | `uuid` | `reason` (≤10000 chars) | `destructiveHint: true`; body `{reason}` |
| `calendly_list_user_busy_times` | `GET /user_busy_times` | `user` (uri), `start_time`, `end_time` | — | **Window ≤ 7 days** (Calendly's documented limit) — validated client-side, `invalid_argument` otherwise; no pagination (Calendly: "does not support traditional keyset pagination") |
| `calendly_create_scheduling_link` | `POST /scheduling_links` | `owner` (event type uri) | `max_event_count` (default 1) | Returns `{booking_url, owner, owner_type}` |

Error envelope (every tool, on failure):
```json
{"error": {"code": "unauthorized|not_found|invalid_argument|rate_limited|upstream_error", "message": "...", "retryable": false}}
```
mapped from Calendly's `{"title": "...", "message": "...", "details": [{"parameter": "...", "message": "...", "code": "..."}]}` plus HTTP status (401/403→`unauthorized`, 404→`not_found`, 400/422→`invalid_argument`, 429→`rate_limited`/`retryable:true`, 5xx→`upstream_error`/`retryable:true`).

No database, no migration — this service is stateless; Calendly is the system of record.

**Backward compatibility**: new repo, no existing consumers; nothing to stay compatible with. Per §1.2 of `mcp-track.md`, no cross-repo header/field dependency is introduced by this ticket (gateway forwards whatever header is registered; no platform-side change).

### Key flow / sequence

```
Agent -> Gateway -> POST /mcp (tools/call, X-Calendly-Api-Key header) -> calendly-mcp
  middleware: header present? no -> 401 {error} back to Gateway
  middleware: header present -> set token in ContextVar
  tools.py: validate args (e.g. date window) -> invalid -> {error: invalid_argument}
  tools.py: client.py -> GET/POST https://api.calendly.com/<path> (Authorization: Bearer <token>)
  Calendly 2xx -> tools.py shapes compact JSON -> MCP result
  Calendly 4xx/5xx -> errors.py maps -> {error: ...} MCP result (never an uncaught exception)
  finally: ContextVar reset (no token/data persists past this request)
```

### Non-functional

- **Idempotency & concurrency**: all GET tools are naturally idempotent (read-only, `readOnlyHint: true`). `calendly_cancel_scheduled_event` is the only state-changing tool besides link creation; canceling an already-canceled event is idempotent at Calendly's API level (it returns the already-canceled state or a 4xx this service passes through — no custom dedupe logic needed). `calendly_create_scheduling_link` is additive (each call makes a new link) — not idempotent by nature, matches Calendly's own semantics, no MSPbots-side workaround needed.
- **Performance**: all list tools default to Calendly's own default page size (20, cap 100) to stay within the SOP's ≤20000-char response budget; `calendly_list_user_busy_times` has no pagination upstream, bounded by the 7-day window instead. Outbound timeouts 5s connect / 30s read per SOP; retries capped so one tool call never exceeds ~120s total per SOP §5.
- **Security**: credential is a single Header-scoped Personal Access Token per SOP's "credentials only from a request header" rule; never logged, never written to disk, never cached beyond the request's `ContextVar` lifetime. No gateway or control-plane change — this is a standard Header-credential vendor, not OAuth, so `mcp-manager`/`mcp-service-gateway` need no special-casing (§6 of `mcp-track.md` does not apply).
- **Multi-tenant isolation**: the entire isolation model is "no shared state" — `contextvars.ContextVar` set per-request and reset in `finally`, no global/module-level client or cache holds a token or a prior response (AC12). This is the SOP's standard contract (§3.3/§3.4), not a new mechanism designed for this ticket.
- **Observability**: structured log line per tool call: tool name, Calendly HTTP status, error `code` if any, latency — no token, no invitee PII beyond what the agent already requested, consistent with SOP §0.4/§11 ("no real credentials in the repo", by extension no credentials in logs).

### Decisions made by DEV01

No one is available to ask during this unattended run; the following choices were made and are reversible by a follow-up comment + moving the ticket back to `5b - ready for groom`:

- **Credential mechanism: Personal Access Token via `X-Calendly-Api-Key` header, not OAuth.** Why: Calendly's API accepts both an OAuth2 bearer token and a Personal Access Token under the identical `Authorization: Bearer <token>` scheme (`securitySchemes` in the OpenAPI spec) — a PAT needs no redirect flow and fits the SOP's "credentials only from a request header" contract with zero extra moving parts. Alternative not chosen: OAuth2 app registration with Calendly, which would need a redirect/callback surface this stateless service does not have and a gateway-side OAuth flow (out of scope, would need Leo per `mcp-track.md` §6). This carries forward the same decision already recorded in the prior `[BLOCKED]` comment's README draft, so it is not a new call, just confirmed.
- **Tool cut: 9 tools, scheduling-only** (see Goals/Non-goals). Why: matches the ticket title `[Scheduling] Calendly` and keeps the service under the SOP's 20-tool ceiling with room to grow; admin/CRM/compliance endpoints (contacts, routing forms, webhooks, team management, activity log, data-compliance deletion) are a different capability class an agent doing "scheduling" would not need. Alternative not chosen: wrapping all ~35 documented endpoints — rejected as scope creep past what the ticket asks for and would push the tool count close to the SOP ceiling with tools nobody asked for.
- **No webhook subscription tool.** Why: a webhook tool would require this stateless, no-public-endpoint service to either expose a public callback URL (contradicts SOP §1 "not exposed to the public internet") or proxy webhook registration to some other receiver that does not exist yet. Real-time notification is a separate feature, not "connect Calendly for scheduling".
- **Pagination defaults mirror Calendly's own** (default 20, cap 100) rather than inventing a different MSPbots-wide default. Why: Calendly's own default/cap are already well inside the SOP's recommended ≤50 default / ≤200 hard cap, so there is no reason to diverge and create a second thing to document.
- **`calendly_create_scheduling_link` instead of `POST /invitees` (Scheduling API).** Why: the ticket's framing ("live access… to help with scheduling") implies the agent helps arrange a meeting, which in Calendly's model means generating a link someone else uses to pick their own slot — not the agent silently booking a slot on a human's behalf without their presence on Calendly's booking page. `POST /invitees` is documented as part of completing a booking that is already happening on a Calendly page (the embed flow), not a generic "create this invitee" action a connector should expose standalone.
